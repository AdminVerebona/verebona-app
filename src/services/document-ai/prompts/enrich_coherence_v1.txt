## MISSION A — SUGGESTIONS DE VALEURS (champs vides uniquement)
════════════════════════════════════════════════════════════

**R1 — Zéro invention** : Ne suggère QUE ce qui est textuellement dans les documents.

**R1a — ROUTAGE ACTIF PAR BIEN** : Les documents peuvent contenir des informations sur PLUSIEURS biens (ex: une facture listant plusieurs véhicules, un document groupé). Tu dois IDENTIFIER ACTIVEMENT quelles données appartiennent au bien **{{ASSET_NAME}}** :

- **Pour les véhicules** : marque, modèle, plaque d'immatriculation, kilométrage associé
- **Pour l'immobilier** : adresse, nom, lot, référence cadastrale
- **Pour les objets** : nom du produit, marque, numéro de série
- **Structure** : sous-totaux, tableaux, sections dédiées

⚠️ **RÈGLE ABSOLUE** : N'extrais QUE les données du bien {{ASSET_NAME}}. Si une information concerne clairement un autre bien mentionné dans le même document, ignore-la. En cas de doute, omets plutôt que de risquer une contamination entre biens.

**R2 — Zéro valeur vide** : N'inclus un champ que si tu as une valeur concrète.

**R3 — Zéro champ déjà renseigné** : Ne propose PAS en mission A un champ qui a déjà une valeur.

**R4 — Calibration de la confiance** : "high" = valeur écrite noir sur blanc ; "medium" = déductible ; "low" = probable.

Voir les définitions des champs et valeurs autorisées en fin de prompt.

## MISSION B — CORRECTION DES VALEURS EXISTANTES (champs déjà renseignés)
════════════════════════════════════════════════════════════

Compare chaque valeur de la liste "Champs déjà renseignés" avec ce que disent les documents. Pour chaque divergence :

1. **Si un document fiable contredit explicitement la valeur stockée** → fournis une `coherenceUpdate` avec la valeur corrigée.
   Ex : `acquisitionPrice = 250000` mais l'acte notarié mentionne 320000 → met à jour à 320000.
   Ex : `mileage = 45000` mais un CT récent indique 98000 → met à jour à 98000.
   Ex : `insuranceExpiry = 2023-01-01` mais un avenant récent prolonge jusqu'en 2025 → met à jour.

2. **Si l'information est ambiguë, contradictoire entre plusieurs documents, ou insuffisante pour trancher** → crée une alerte de cohérence sans modifier.
   Ex : plusieurs documents donnent des valeurs différentes et aucun n'est clairement plus fiable.
   Ex : la valeur stockée est plausible mais les documents ne permettent pas de la confirmer ou infirmer clairement.
   
   **Pour chaque alerte, explique clairement** :
   - Quelle est la valeur stockée et d'où elle vient probablement
   - Ce que le(s) document(s) indique(nt) à la place
   - Pourquoi on ne peut pas corriger automatiquement (documents contradictoires, date inconnue, source peu fiable)
   - Ce que l'utilisateur devrait vérifier ou faire

**Ne modifie PAS et ne signale PAS** :
- Les champs vides (c'est la mission A).
- Les différences de format (ex: "Rue de la Paix" vs "rue de la paix").
- Les approximations acceptables (surface à ±2 m² près).
- Les champs pour lesquels les documents ne donnent aucune information.

## MISSION C — COHÉRENCE AGENDA
════════════════════════════════════════════════════════════

Analyse les événements agenda listés ci-dessus (section "Événements agenda liés à ce bien").
Tu dois détecter les relations entre eux et proposer des actions.

**C1 — Relations de dépendance ou succession logique** : deux événements proches dans le temps
concernant le même bien, où le premier est une étape préparatoire du second.
→ Exemple : "Gardiennage des pneus" le 20 juin suivi de "Remplacement des pneus" le 24 juin
  → le gardiennage est probablement déjà réalisé (les pneus ont été récupérés pour être remplacés).
→ Dans ce cas, suggère `mark_realise` pour l'événement préparatoire.

**C2 — Doublon** : deux événements avec le même libellé sensiblement à la même date.
→ Signaler sans marquer comme réalisé.

**Règles** :
- Ne proposer que des actions avec une confiance ≥ 0.7.
- Ne pas proposer `mark_realise` pour un événement dont la date est encore dans le futur,
  sauf s'il y a une relation claire de dépendance avec un événement postérieur.
- Si un événement est déjà "réalisé" ou "annulé", ignorer.

## DÉFINITIONS ET VALEURS AUTORISÉES
════════════════════════════════════════════════════════════

### Champs communs
- `description` : description synthétique du bien (1-3 phrases), PAS une copie du texte brut.
- `acquisitionDate` : UNIQUEMENT date d'achat visible dans un acte de vente notarié.
- `acquisitionPrice` : UNIQUEMENT prix d'achat dans un acte de vente.
- `charges` : UNIQUEMENT charges de copropriété, PAS une facture de travaux.
- `monthlyRent` : UNIQUEMENT loyer mensuel si le bien est loué, PAS un prix d'achat.
- `estimatedValue` : valorisation estimée par un professionnel, PAS un prix d'achat.
- `acquisitionLocation` : lieu géographique de l'acquisition, PAS l'adresse du bien.
- `estimatedValueDate` : date de l'estimation, PAS date d'achat ni date du document.
- `estimatedValueMode` : mode d'estimation (ESTIMATION_AGENCE, EXPERTISE_NOTARIALE, etc.)

### Véhicules
- `registrationNumber` : plaque d'immatriculation (format AA-123-BB).
- `mileage` : kilométrage au compteur, PAS la puissance ou le PTAC.
- `vehicleOwnershipStatus` : PROPRIETAIRE, LLD, LOA, CREDIT, PRET_GRATUIT.
- `insuranceContractNumber` : numéro de contrat assurance.
- `insuranceClientNumber` : numéro de client chez l'assureur.
- `insurancePremium` : prime annuelle TTC en nombre décimal.

### Valeurs autorisées (enum)
- generalCondition / condition : NEUF, BON, MOYEN, MAUVAIS
- occupancyUsage : RESIDENCE_PRINCIPALE, RESIDENCE_SECONDAIRE, LOCATIF, VACANT
- occupancyStatus : PROPRIETAIRE, LOCATAIRE, OCCUPANT_GRATUIT, USUFRUITIER
- vehicleOwnershipStatus : PROPRIETAIRE, LLD, LOA, CREDIT, PRET_GRATUIT
- estimatedValueMode : ESTIMATION_AGENCE, EXPERTISE_NOTARIALE, EXPERTISE_INDEPENDANTE, AVIS_VALEUR, SIMULATION_OUTIL, ESTIMATION_PERSONNELLE
- dpeClass / gesClass : A, B, C, D, E, F, G
- fuelType : ESSENCE, DIESEL, ELECTRIQUE, HYBRIDE, GPL, AUTRE
- mileageUnit : km, mi, h
- isInsured : true, false
