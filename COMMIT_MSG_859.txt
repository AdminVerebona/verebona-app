#859 — Achats : provenance du titre au niveau du champ (Opération et Agenda) — titre USER protégé, titre SYSTEM améliorable malgré une correction de date

- Brique unique `business-operations/title-provenance.ts` : états SYSTEM / USER / INCONNU par champ (`operationTitleAuthority`, `agendaTitleAuthority`, garde SQL `AGENDA_TITLE_SYSTEM_SQL`, colonnes de preuve, `loadOperationTitleAuthority`, déclaration `declareTitleWrite(Pg)`) ; jamais SYSTEM par égalité de chaînes ni USER par le seul indicateur global ; repli du stock sur l'historique de l'opération et les traces USER_MODIFIED de l'Agenda, sinon INCONNU
- Migrations 2010 (Opération) / 2011 (Agenda) additives et idempotentes : `title_provenance` (JSONB) sur `business_operations` et `agenda_items`, tenue par déclencheurs BEFORE … UPDATE OF dans la même instruction que l'écriture du titre, d'après une déclaration locale à la transaction (`verebona.title_declaration`) ; écriture non déclarée : provenance effacée (Opération) ou règles prudentes (Agenda) ; aucun titre réécrit, aucune conversion du stock
- T3 : `acquisitionLabelDecision` décidée par l'autorité du champ (plus `fullyManaged`, `porte`, `recordedLabel`) — création, reconsolidation, branche de retrait de source (achat), `acquisitionNameFor`, `previewAcquisitionNames`, `applyAcquisitionNames` (décision recalculée sous le verrou du compte) ; écritures T3 / reprise déclarées SYSTEM, commandes de l'utilisateur USER (valeur réellement changée seulement)
- T4 : renommage d'un achat dissocié de `isTouched` — DOCUMENT (RETITLE) et OPERATION (SYNC si intacte, RETITLE du titre seul si date corrigée) ; gardes indépendantes conservées (« à qualifier », prévision, consolidation restaurée, type, autre opération, élément saisi) ; écrivain `retitleAgendaItem` gardé par `PURCHASE_RETITLE_SQL` (provenance, valeur attendue, compte, rattachement, achat actif) sans assouplir `ABSORBABLE_SQL` ; restauration RETITLE jamais par-dessus un titre choisi ; CREATE / SYNC déclarés SYSTEM
- Agenda utilisateur : `updateAgendaItem` déclare USER un titre réellement changé (titulaire, membre Duo, Assistant) ; titre renvoyé inchangé : aucune fausse provenance USER
- Reprise `purchase-title-reprise.ts` : diagnostic par titre (état, motif, preuve, `blockedExpected`), actions KEEP_UNKNOWN_PROVENANCE, compteur `keptUnknown` (script 821) ; aucune carte « À traiter » pour la seule incertitude
